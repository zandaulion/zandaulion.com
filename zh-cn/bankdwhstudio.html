问题变成了你可以检查的东西

Bank DWH Studio 是一个个人概念验证项目，用自然语言探索大型银行数据仓库。提出问题，按需选择一个银行业务领域，再决定回答方式：由智能体查找数据表并测试 SQL，或由流水线检索模式并一步写出 PostgreSQL SQL。

结果特意不只是一段代码。可编辑的草稿旁边会显示所用的数据表、理解、假设、审核备注和基本检查，以及草稿从数据仓库合成副本中返回的行。缺少必要信息时，例如关于八月底的请求没有写年份，助手可以请你澄清。

它是如何运作的

  1. 用日常用语提问。 描述你需要的银行业务答案，必要时把搜索限定在某个领域，并基于之前的回答继续追问。
  2. 让智能体去查。 在智能体模式下，模型会搜索数据表索引，阅读打算使用的数据表的定义，在数据仓库上测试草稿，并在回答前修正数据库拒绝的部分。
  3. 或一步写出。 在流水线模式下，Node 后端从 Elasticsearch 检索模式中有限的一部分，模型据此在一次调用中写出草稿，另有基于目录的规则处理少数常见问题。
  4. 使用前请检查。 实时查看智能体的每一步，然后编辑或复制草稿，检查它返回的行，并审视其上下文和假设。

工作台上有什么

100张合成桌子

生成的银行仓库固定装置提供 5,000 个列、关系、PostgreSQL DDL、目录和小种子。

两种回答方式

由智能体查找数据表并测试 SQL，或由流水线从 Elasticsearch 检索模式并在一次调用中写出草稿。每位用户自行选择模式。

在只读副本上测试

草稿在基准测试的合成数据仓库上运行，该仓库已填充数据，运行身份是只能读取的用户，时限 15 秒，并限制行数。每次启动都会从种子数据重建副本。

可见的推理上下文

检索到的表格、解释、假设、注释和检查保持可见，因此草案可以受到质疑，而不是盲目接受。

可随时回看的回答

每条回答，包括向你提出的追问，都会保存在你设备上的历史记录中。你可以恢复之前的草稿，或删除不再需要的记录。

内置模型测试

两个标签页展示每一次基准测试运行，并标明是开放权重还是封闭权重；可将结果导出为 PDF，并允许获批设备在租用的 GPU 上或通过 OpenRouter 测试新模型，实时显示进度。

每一步都有记录

只追加的审计日志会记录每个问题、每条执行的语句及其执行者，以及每个回答，并与设备上的历史记录分开保存。

一台PWA，多个屏幕

仅限邀请的界面是可安装的，并且适用于从宽桌面屏幕到紧凑型手机。

用测量说话，而非假设

写 SQL 的工具只有在 SQL 正确时才有用，所以代码库会实际测量这一点，而不是想当然。

模型基准测试提出 46 个难题，每题问三次。只有一个正确答案的问题，通过在填充了数据的 PostgreSQL 数据仓库副本上运行草稿来评分。对于数据仓库中没有的数据（例如薪资或客户流失）的问题，应当以追问作答。修改数据的请求绝不能到达用户。

最重要的指标是模型“自信地答错”的频率：草稿能运行却返回错误结果，或者针对不存在的数据给出答案。两者看起来都像真实答案，这正是它们的风险所在。

每个模型都会把同一组问题回答两遍。第一遍，数据仓库使用描述性名称，例如 fact_account_balance_daily。第二遍，使用像老式银行数据仓库那样缩写的晦涩名称，例如 F_ACCT_BAL_D，但保留列描述。数据和正确答案保持不变。

使用描述性名称

  • gpt-oss-20b，应用所用的模型： 正确率 86%，5 次自信地答错，在一块 A100 上每分钟约处理 200 个问题。
  • Qwen3.8-27B： 正确率 96%，没有一次自信地答错，但速度慢约五倍。
  • gpt-oss-120b： 并不比 20b 更准确，速度却不到其一半。

这三个模型在该追问时都进行了追问，而 SQL 检查拦截了 gpt-oss-20b 尝试的每一次写入。

使用晦涩名称

每个开放模型都下降了 22 到 39 个百分点。新出现的错误恰恰是可读名称原本能避免的：猜错的列，或因缩写而误读的表。没有一个开放模型放行过写入。

  • gpt-oss-20b： 正确率从 86% 降到 46%，有 17 次自信地答错。
  • Qwen3.8-27B： 最好的开放模型，正确率 70%，8 次自信地答错。
  • Gemini 3.8 Flash： 所有模型中最好的，正确率 72%，只有一次自信地答错，因为它宁可追问也不瞎猜。
  • Claude Sonnet 5、GPT-5.5 和 GPT-4.1： 正确率 68% 到 70%，但有 9 到 18 次自信地答错。
  • GPT-6 Luna： 过于谨慎：69 个问题中有 53 个以追问作答，正确率只有 22%。

封闭模型仅用于比较。它们无法在银行自己的硬件上运行，因此通过 OpenRouter 调用。开放权重模型在租用的 GPU 上用 vLLM 运行，结束后删除 GPU，通常不超过 12 分钟，花费远低于一美元。

智能体还是流水线

从十月起，应用也可以作为智能体回答，基准测试会用相同的问题、数据和模型运行两种模式。它新增了 17 道更难的问题，例如某条记录在过去某一日期的历史、按每日汇率换算货币、中位数，以及每个季度都活跃的客户。这些测试在 A100 上使用晦涩名称，每道题问三次。

自信地答错统计的是智能体在原有 23 题以及关于不存在数据的问题上的错误。回答时间为中位数。作为对比，以流水线方式运行的闭源模型在更难问题上的得分为：Claude Sonnet 5 71%，Gemini 3.8 Flash 69%，GPT-4.1 mini 55%，GPT-4.1 49%，GPT-6 Luna 22%，因为它对大多数问题都会反问。每个以智能体方式运行的开源模型，得分都高于任何以流水线方式运行的闭源模型。

提升从何而来

把智能体拆开来看，用 gpt-oss-20b 回答原有 23 题，就能看出每个部分的贡献。

  • 查找数据表让它更安全： 在执行任何内容之前，自信地答错的回答就从 17 个降到 3 或 4 个，因为智能体能找到流水线搜索从未返回的数据表。
  • 测试草稿让它更正确： 如果无法运行自己的 SQL，大约一半的草稿会失败，主要是猜错了日期表的列。数据库的错误信息足以修正这些问题，只用 EXPLAIN 检查、一行数据都不看，也几乎保留了全部提升。
  • 业务规则没有可测量的作用： 去掉提供给智能体的那份简短银行业务规则，它的表现同样好。
  • 代价是令牌和时间： 一个智能体问题消耗的令牌是流水线问题的数倍，耗时是其两到三倍。

在更难的问题上，gpt-oss-20b 的错误是能运行但返回错误答案的草稿，测试无法发现这类错误。

同一模型，不同服务器

该应用可连接任何兼容 OpenAI 的端点，因此从托管服务商切换到银行自己的服务器，看起来只是简单的配置更改。一个独立的评估工具会验证事实是否如此。同一套 gpt-oss-20b 权重分别由托管服务商、在 CPU 上，以及在租用的 GPU 上通过 llama.cpp、vLLM 和 SGLang 提供服务。

每个服务器都选对了表。差异出现在其他方面：草稿添加了哪些可选连接，破坏性请求是被直接拒绝还是稍后被 SQL 检查拦截，以及在负载下的表现。vLLM 在 64 个并发请求下仍遵守严格的 JSON 格式，在单块 RTX 4090 上达到每分钟约 270 个问题。SGLang 在负载下破坏了该格式，直到使用更严格的设置启动才解决；而这种故障在逐个请求时从未出现。

另一项实验用大型机风格的缩写名称重写了目录。保留表和列的描述时，两个模型仍通过了全部十二个基准问题。去掉描述后，只有一半通过，这清楚地表明，优质的元数据与模型同样重要。

人类留在循环中

应用会编写并测试 SQL 草稿，但只在数据仓库的合成副本上进行，且以只能读取的用户身份运行；它从不连接真实的银行数据仓库。用户仍需审核结果，再编辑或复制，并在自己的数据库客户端中运行。浏览器永远不会收到模型的 API 密钥。

自动检查仅涵盖只读语句的基本形态和已知表引用。SQL 语法、字段引用和业务含义仍须人工审查。仓库中的所有名称、关系和指标都是合成测试材料，并非获批准的银行业务定义。

在引擎盖下

已部署的概念验证在 Oracle Ampere A1 实例上以无 root 权限容器运行 Node 后端、Elasticsearch 和只读的 PostgreSQL 数据仓库，并通过托管服务商使用 gpt-oss-20b 编写 SQL。代码库还记录了一个更宏大的未来架构，与已部署的小型 POC 明确分开。
