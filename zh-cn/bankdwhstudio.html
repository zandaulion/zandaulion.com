问题变成了你可以检查的东西

Bank DWH Studio 是通过自然语言探索大型银行数据仓库的个人概念证明。提出问题，可选择选择银行主题领域，应用程序会在起草 PostgreSQL SQL 之前检索最相关的架构上下文。

结果故意不仅仅是一个代码块。它显示了检索到的表格、解释、假设、审查注释和可编辑草稿旁边的基本检查。当缺少必要的细节时（例如八月底请求中的年份），助理可以要求澄清。

它是如何运作的

  1. 用日常用语提问。 描述您需要的银行业答案，并在有用时将搜索范围缩小到某个主题领域。
  2. 检索模式的有界切片。 Node 后端在 Elasticsearch 元数据中搜索相关表和列。
  3. 草稿与上下文。 托管的 GPT-OSS 模型从该有界架构创建 SQL，而基于目录的规则则处理支持的常见问题。
  4. 使用前请检查。 编辑或复制草稿，检查其上下文和假设，然后在您自己的 SQL 客户端中单独运行它。

工作台上有什么

100张合成桌子

生成的银行仓库固定装置提供 5,000 个列、关系、PostgreSQL DDL、目录和小种子。

基于模式的检索

在将任何内容发送到模型之前，Elasticsearch 将大型目录缩小到问题所需的元数据。

可见的推理上下文

检索到的表格、解释、假设、注释和检查保持可见，因此草案可以受到质疑，而不是盲目接受。

可随时回看的回答

每条回答，包括向你提出的追问，都会保存在你设备上的历史记录中。你可以恢复之前的草稿，或删除不再需要的记录。

内置模型测试

两个标签页展示每一次基准测试运行，并标明是开放权重还是封闭权重；可将结果导出为 PDF，并允许获批设备在租用的 GPU 上或通过 OpenRouter 测试新模型，实时显示进度。

一台PWA，多个屏幕

仅限邀请的界面是可安装的，并且适用于从宽桌面屏幕到紧凑型手机。

用测量说话，而非假设

写 SQL 的工具只有在 SQL 正确时才有用，所以代码库会实际测量这一点，而不是想当然。

模型基准测试提出 46 个难题，每题问三次。只有一个正确答案的问题，通过在填充了数据的 PostgreSQL 数据仓库副本上运行草稿来评分。对于数据仓库中没有的数据（例如薪资或客户流失）的问题，应当以追问作答。修改数据的请求绝不能到达用户。

最重要的指标是模型“自信地答错”的频率：草稿能运行却返回错误结果，或者针对不存在的数据给出答案。两者看起来都像真实答案，这正是它们的风险所在。

每个模型都会把同一组问题回答两遍。第一遍，数据仓库使用描述性名称，例如 fact_account_balance_daily。第二遍，使用像老式银行数据仓库那样缩写的晦涩名称，例如 F_ACCT_BAL_D，但保留列描述。数据和正确答案保持不变。

使用描述性名称

  • gpt-oss-20b，应用所用的模型： 正确率 86%，5 次自信地答错，在一块 A100 上每分钟约处理 200 个问题。
  • Qwen3.8-27B： 正确率 96%，没有一次自信地答错，但速度慢约五倍。
  • gpt-oss-120b： 并不比 20b 更准确，速度却不到其一半。

这三个模型在该追问时都进行了追问，而 SQL 检查拦截了 gpt-oss-20b 尝试的每一次写入。

使用晦涩名称

每个开放模型都下降了 22 到 39 个百分点。新出现的错误恰恰是可读名称原本能避免的：猜错的列，或因缩写而误读的表。没有一个开放模型放行过写入。

  • gpt-oss-20b： 正确率从 86% 降到 46%，有 17 次自信地答错。
  • Qwen3.8-27B： 最好的开放模型，正确率 70%，8 次自信地答错。
  • Gemini 3.8 Flash： 所有模型中最好的，正确率 72%，只有一次自信地答错，因为它宁可追问也不瞎猜。
  • Claude Sonnet 5、GPT-5.5 和 GPT-4.1： 正确率 68% 到 70%，但有 9 到 18 次自信地答错。
  • GPT-6 Luna： 过于谨慎：69 个问题中有 53 个以追问作答，正确率只有 22%。

封闭模型仅用于比较。它们无法在银行自己的硬件上运行，因此通过 OpenRouter 调用。开放权重模型在租用的 GPU 上用 vLLM 运行，结束后删除 GPU，通常不超过 12 分钟，花费远低于一美元。

报告还逐题列出了结果，晦涩名称的代价在那里一目了然。使用晦涩名称时，没有任何模型答对五个问题，而 Qwen3.8-27B 在描述性名称下每次都答对，例如逾期超过 90 天的贷款有多少笔。

同一模型，不同服务器

该应用可连接任何兼容 OpenAI 的端点，因此从托管服务商切换到银行自己的服务器，看起来只是简单的配置更改。一个独立的评估工具会验证事实是否如此。同一套 gpt-oss-20b 权重分别由托管服务商、在 CPU 上，以及在租用的 GPU 上通过 llama.cpp、vLLM 和 SGLang 提供服务。

每个服务器都选对了表。差异出现在其他方面：草稿添加了哪些可选连接，破坏性请求是被直接拒绝还是稍后被 SQL 检查拦截，以及在负载下的表现。vLLM 在 64 个并发请求下仍遵守严格的 JSON 格式，在单块 RTX 4090 上达到每分钟约 270 个问题。SGLang 在负载下破坏了该格式，直到使用更严格的设置启动才解决；而这种故障在逐个请求时从未出现。

另一项实验用大型机风格的缩写名称重写了目录。保留表和列的描述时，两个模型仍通过了全部十二个基准问题。去掉描述后，只有一半通过，这清楚地表明，优质的元数据与模型同样重要。

人类留在循环中

应用只生成 SQL 草稿；它不会连接银行数据仓库，也不会执行查询。用户可编辑或复制结果，再在自己的数据库客户端中单独运行。浏览器不会收到模型 API 密钥。

自动检查仅涵盖只读语句的基本形态和已知表引用。SQL 语法、字段引用和业务含义仍须人工审查。仓库中的所有名称、关系和指标都是合成测试材料，并非获批准的银行业务定义。

在引擎盖下

已部署的概念验证在 Oracle Ampere A1 实例上以 rootless 容器运行 Node 后端和 Elasticsearch，并通过托管服务商使用 gpt-oss-20b 起草 SQL。代码库还记录了一个更广泛的未来架构，与规模更小的已部署 POC 明确区分。
