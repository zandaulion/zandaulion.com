Bank DWH Studio

은행 데이터에 대해 질문하고 관련 스키마를 살펴본 뒤 편집 가능한 SQL 초안을 받아 보세요.

PWA 열기 GitHub에서 보기

라이브 PWA는 초대 전용입니다.

질문은 검사할 수 있는 것이 됩니다

Bank DWH Studio는 자연어를 통해 대규모 은행 데이터 웨어하우스를 탐색하기 위한 개인 개념 증명입니다. 질문하고 선택적으로 은행 주제 영역을 선택하면 앱이 PostgreSQL SQL 초안을 작성하기 전에 가장 관련성이 높은 스키마 컨텍스트를 검색합니다.

결과는 의도적으로 코드 블록 그 이상입니다. 편집 가능한 초안 옆에 검색된 테이블, 해석, 가정, 검토 메모 및 기본 점검 사항이 표시됩니다. 8월 말 요청의 연도와 같이 필요한 세부 정보가 누락된 경우 도우미는 설명을 요청할 수 있습니다.

작동 원리

  1. 일상 언어로 물어보세요. 필요한 뱅킹 답변을 설명하고 유용할 경우 주제 영역으로 검색 범위를 좁히세요.
  2. 스키마의 제한된 조각을 검색합니다. Node 백엔드는 Elasticsearch 메타데이터에서 관련 테이블 및 열을 검색합니다.
  3. 맥락을 고려한 초안. 호스팅된 GPT-OSS 모델은 제한된 스키마에서 SQL를 생성하는 반면 카탈로그 기반 규칙은 지원되는 일반적인 질문을 처리합니다.
  4. 사용하기 전에 검토하십시오. 초안을 편집하거나 복사하고, 해당 컨텍스트와 가정을 검사한 다음, 자체 SQL 클라이언트에서 별도로 실행하세요.

작업대에는 무엇이 있나요?

100개의 합성 테이블

생성된 은행 창고 고정 장치는 5,000개의 열, 관계, PostgreSQL DDL, 카탈로그 및 작은 시드를 제공합니다.

스키마 기반 검색

Elasticsearch는 모델에 항목을 보내기 전에 질문에 필요한 메타데이터로 대규모 카탈로그를 좁힙니다.

가시적 추론 맥락

검색된 표, 해석, 가정, 메모 및 점검 사항은 눈에 잘 띄므로 초안을 맹목적으로 받아들이는 대신 이의를 제기할 수 있습니다.

다시 볼 수 있는 답변

사용자에게 되묻는 질문을 포함해 모든 답변이 기기의 기록에 저장됩니다. 이전 초안을 복원하거나 더 이상 필요 없는 항목을 삭제할 수 있습니다.

모델 테스트 기본 제공

두 개의 탭에서 모든 벤치마크 실행을 보여 주고 결과를 PDF로 내보내며, 승인된 기기는 대여한 GPU에서 새 모델을 테스트하고 진행 상황을 실시간으로 볼 수 있습니다.

하나의 PWA, 많은 화면

초대 전용 인터페이스는 설치가 가능하며 넓은 데스크톱 화면에서 소형 휴대폰까지 적용됩니다.

가정이 아닌 측정

SQL을 작성하는 도구는 그 SQL이 정확할 때만 쓸모가 있습니다. 그래서 저장소는 이를 당연하게 여기지 않고 직접 측정합니다.

모델 벤치마크는 46개의 어려운 질문을 각각 세 번씩 묻습니다. 정답이 하나인 질문은 데이터를 채운 PostgreSQL 웨어하우스 사본에서 초안을 실행해 채점합니다. 급여나 고객 이탈처럼 웨어하우스에 없는 데이터에 관한 질문에는 되묻는 것이 정답입니다. 데이터를 변경하려는 요청은 절대 사용자에게 전달되어서는 안 됩니다.

가장 중요한 수치는 모델이 자신 있게 틀리는 빈도입니다. 실행은 되지만 틀린 결과를 내는 초안, 또는 존재하지 않는 데이터에 대한 답변이 여기에 해당합니다. 둘 다 진짜 답처럼 보이기 때문에 위험합니다.

  • gpt-oss-20b, 앱이 사용하는 모델: 정답률 86%, 자신 있게 틀린 답변 5건, A100 한 대에서 분당 약 200개 질문.
  • Qwen3.8-27B: 정답률 96%에 자신 있게 틀린 답변은 없지만, 속도는 약 5배 느립니다.
  • gpt-oss-120b: 20b보다 정확하지 않으며 속도는 절반에도 못 미칩니다.

세 모델 모두 되물어야 할 때마다 되물었고, gpt-oss-20b가 시도한 모든 쓰기는 SQL 검사가 막아냈습니다. 각 벤치마크 실행은 GPU를 대여해 vLLM으로 모델을 제공하고, 끝나면 GPU를 삭제합니다. 보통 12분 이내에 끝나며 비용은 1달러에 한참 못 미칩니다.

같은 모델, 다른 서버

앱은 OpenAI 호환 엔드포인트라면 어디든 연결할 수 있어서, 호스팅 제공업체에서 은행 자체 서버로 옮기는 일이 단순한 설정 변경처럼 보입니다. 별도의 평가 도구가 실제로 그런지 확인합니다. 같은 gpt-oss-20b 가중치를 호스팅 제공업체, CPU, 그리고 llama.cpp, vLLM, SGLang을 사용하는 대여 GPU에서 각각 제공했습니다.

모든 서버가 올바른 테이블을 골랐습니다. 차이는 다른 곳에서 나타났습니다. 초안에 추가되는 선택적 조인, 파괴적인 요청이 바로 거부되는지 아니면 나중에 SQL 검사에서 걸러지는지, 그리고 부하 상황에서였습니다. vLLM은 동시 요청 64개에서도 엄격한 JSON 형식을 지켰고, RTX 4090 한 장에서 분당 약 270개 질문을 처리했습니다. SGLang은 부하가 걸리면 이 형식을 깨뜨렸고, 더 엄격한 설정으로 시작한 뒤에야 해결되었습니다. 이 오류는 요청을 하나씩 보낼 때는 한 번도 나타나지 않았습니다.

또 다른 실험에서는 카탈로그를 메인프레임 스타일의 약어 이름으로 바꿨습니다. 테이블과 열 설명을 유지했을 때는 두 모델 모두 기준 질문 12개를 모두 통과했습니다. 설명을 없애자 절반만 통과했는데, 이는 좋은 메타데이터가 모델만큼 중요하다는 분명한 신호입니다.

갤러리

벤치마크에서 고른 어려운 질문 10개를 넓은 데스크톱부터 작은 휴대폰까지 보여 줍니다. 각 SQL 초안은 앱 자체의 파이프라인과 모델이 작성했고, 데이터를 채운 웨어하우스에서 실행해 검증했습니다. 10개 모두 정답을 냈습니다. 스크린샷은 이렇게 기록된 응답을 재생한 것이므로 재현할 수 있으며 실제 은행 데이터는 포함하지 않습니다.

인간은 루프에 머무른다

앱은 SQL 초안만 작성하며 은행 데이터 웨어하우스에 연결하거나 쿼리를 실행하지 않습니다. 사용자는 결과를 편집하거나 복사한 뒤 자신의 데이터베이스 클라이언트에서 별도로 실행합니다. 브라우저에는 모델 API 키가 전달되지 않습니다.

자동 검사는 읽기 전용 명령문의 기본 형태와 알려진 테이블 참조만 확인합니다. SQL 구문, 열 참조, 비즈니스 의미는 여전히 사람이 검토해야 합니다. 웨어하우스의 모든 이름, 관계, 측정값은 합성 테스트 자료이며 승인된 은행 업무 정의가 아닙니다.

후드 아래

배포된 개념 증명은 Oracle Ampere A1 인스턴스에서 Node 백엔드와 Elasticsearch를 rootless 컨테이너로 실행하고, 호스팅 제공업체를 통해 gpt-oss-20b로 SQL 초안을 작성합니다. 저장소에는 규모가 작은 배포된 POC와 명확히 구분되는 더 넓은 미래 아키텍처도 문서화되어 있습니다.
