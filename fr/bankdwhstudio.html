Une question devient quelque chose que vous pouvez inspecter

Bank DWH Studio est une preuve de concept personnelle pour explorer un vaste entrepôt de données bancaires via le langage naturel. Posez une question, choisissez éventuellement un domaine bancaire et l'application récupère le contexte de schéma le plus pertinent avant de rédiger PostgreSQL SQL.

Le résultat est délibérément plus qu’un bloc de code. Il affiche les tableaux récupérés, l'interprétation, les hypothèses, les notes de révision et les vérifications de base à côté d'un brouillon modifiable. Lorsqu'un détail nécessaire manque, comme l'année dans une demande de fin août, l'assistant peut demander des éclaircissements.

Comment ça marche

  1. Demandez dans le langage courant. Décrivez la réponse bancaire dont vous avez besoin et limitez la recherche à un domaine lorsque cela est utile.
  2. Récupérez une tranche délimitée du schéma. Un backend Node recherche les métadonnées Elasticsearch pour les tables et colonnes pertinentes.
  3. Brouillon avec contexte. Un modèle GPT-OSS hébergé crée SQL à partir de ce schéma limité, tandis que les règles basées sur le catalogue gèrent les questions courantes prises en charge.
  4. Vérifiez avant d'utiliser. Modifiez ou copiez le brouillon, inspectez son contexte et ses hypothèses, puis exécutez-le séparément dans votre propre client SQL.

Mesuré, pas supposé

Un outil qui écrit du SQL n'est utile que si ce SQL est correct : le référentiel le mesure donc au lieu de le tenir pour acquis.

Un benchmark de modèles pose 46 questions difficiles, trois fois chacune. Les questions à réponse unique sont notées en exécutant le brouillon sur une copie PostgreSQL alimentée de l'entrepôt. Les questions sur des données que l'entrepôt ne contient pas, comme les salaires ou l'attrition, doivent recevoir une question en retour. Les demandes de modification des données ne doivent jamais atteindre l'utilisateur.

Le chiffre le plus important est la fréquence à laquelle un modèle se trompe avec assurance : un brouillon qui s'exécute mais donne un mauvais résultat, ou une réponse sur des données qui n'existent pas. Les deux ressemblent à de vraies réponses, et c'est ce qui les rend risqués.

  • gpt-oss-20b, le modèle utilisé par l'application : 86 % de bonnes réponses, 5 réponses fausses avec assurance et environ 200 questions par minute sur un seul A100.
  • Qwen3.8-27B : 96 % de bonnes réponses sans aucune réponse fausse avec assurance, mais environ cinq fois plus lent.
  • gpt-oss-120b : pas plus précis que le 20b, pour moins de la moitié de sa vitesse.

Les trois ont demandé une précision chaque fois qu'il le fallait, et la vérification SQL a intercepté chaque écriture tentée par gpt-oss-20b. Chaque exécution du benchmark loue un GPU, sert le modèle avec vLLM puis supprime le GPU, généralement en 12 minutes au plus et pour bien moins d'un dollar.

Même modèle, serveurs différents

L'application communique avec tout point d'accès compatible OpenAI : passer d'un fournisseur hébergé aux serveurs d'une banque ressemble donc à un simple changement de configuration. Un outil d'évaluation distinct vérifie si c'est vraiment le cas. Les mêmes poids gpt-oss-20b ont été servis par un fournisseur hébergé, sur CPU et sur des GPU loués via llama.cpp, vLLM et SGLang.

Chaque serveur a choisi les bonnes tables. Les différences sont apparues ailleurs : dans les jointures facultatives ajoutées à un brouillon, dans le fait qu'une demande destructive soit refusée ou interceptée plus tard par la vérification SQL, et sous charge. vLLM a respecté le format JSON strict avec 64 requêtes simultanées et a atteint environ 270 questions par minute sur une seule RTX 4090. SGLang a rompu ce format sous charge jusqu'à ce qu'il soit lancé avec un réglage plus strict, une défaillance qui n'est jamais apparue avec une requête à la fois.

Une autre expérience a réécrit le catalogue avec des noms abrégés de style mainframe. En conservant les descriptions des tables et des colonnes, les deux modèles ont encore réussi les douze questions de référence. Sans les descriptions, seule la moitié a réussi : un signe clair que de bonnes métadonnées comptent autant que le modèle.

Galerie

Dix questions difficiles du benchmark, d'un grand écran de bureau à un petit téléphone. Chaque brouillon SQL a été écrit par le pipeline et le modèle de l'application, puis vérifié en l'exécutant sur l'entrepôt alimenté ; les dix ont donné la bonne réponse. L’humain reste au courant

L’application rédige du SQL ; elle ne se connecte jamais à un entrepôt de données bancaire et n’exécute aucune requête. Les utilisateurs modifient ou copient le résultat, puis l’exécutent séparément dans leur propre client SQL. Le navigateur ne reçoit jamais la clé API du modèle.

Les contrôles automatisés vérifient la forme en lecture seule de l’instruction et les références aux tables connues. La syntaxe SQL, les références aux colonnes et le sens métier nécessitent toujours une revue humaine. Tous les noms, relations et indicateurs de l’entrepôt sont des données de test synthétiques, et non des définitions bancaires approuvées.

Sous le capot

La preuve de concept déployée exécute un backend Node et Elasticsearch dans des conteneurs rootless sur une instance Oracle Ampere A1, et rédige le SQL avec gpt-oss-20b via un fournisseur hébergé. Le référentiel documente également une architecture future plus large, clairement séparée du plus petit POC déployé.
