Bank DWH Studio

Ask a banking question. Explore the relevant schema. Leave with an editable SQL draft.

Open the PWA View on GitHub

The live PWA is invitation-only.

A question becomes something you can inspect

Bank DWH Studio is a personal proof of concept for exploring a large banking data warehouse through natural language. Ask a question, optionally choose a banking subject area, and the app retrieves the most relevant schema context before drafting PostgreSQL SQL.

The result is deliberately more than a code block. It shows the retrieved tables, interpretation, assumptions, review notes, and basic checks beside an editable draft. When a necessary detail is missing—such as the year in an end-of-August request—the assistant can ask for clarification.

How it works

  1. Ask in everyday language. Describe the banking answer you need and narrow the search to a subject area when useful.
  2. Retrieve a bounded slice of the schema. A Node backend searches Elasticsearch metadata for relevant tables and columns.
  3. Draft with context. A hosted GPT-OSS model creates SQL from that bounded schema, while catalog-grounded rules handle supported common questions.
  4. Review before using. Edit or copy the draft, inspect its context and assumptions, then run it separately in your own SQL client.

What is on the workbench

100 synthetic tables

A generated banking warehouse fixture provides 5,000 columns, relationships, PostgreSQL DDL, a catalog, and a small seed.

Schema-grounded retrieval

Elasticsearch narrows a large catalog to the metadata needed for the question before anything is sent to the model.

Visible reasoning context

Retrieved tables, interpretation, assumptions, notes, and checks stay visible so the draft can be challenged rather than accepted blindly.

Answers you can return to

Every answer, including a question back to you, is saved to a history on your device. Restore an earlier draft or delete the ones you no longer need.

Model tests, built in

Two tabs show every benchmark run, marked as open or closed weights, export the results as a PDF, and let approved devices test a new model, on a rented GPU or through OpenRouter, with live progress.

One PWA, many screens

The invite-only interface is installable and adapts from wide desktop screens to compact phones.

Measured, not assumed

A tool that writes SQL is only as useful as its SQL is correct, so the repository measures that instead of taking it on trust.

A model benchmark asks 46 hard questions, three times each. Questions with one right answer are scored by running the draft against a seeded PostgreSQL copy of the warehouse. Questions about data the warehouse does not hold, such as salaries or churn, should get a question back. Requests to change data must never reach the user.

The number that matters most is how often a model is confidently wrong: a draft that runs but returns the wrong answer, or an answer about data that does not exist. Both look like real answers, which is what makes them risky.

Every model answers the same questions twice. First the warehouse uses descriptive names, such as fact_account_balance_daily. Then it uses cryptic names, abbreviated the way older bank warehouses spell them, such as F_ACCT_BAL_D, with the column descriptions kept. The data and the right answers stay the same.

With descriptive names

  • gpt-oss-20b, the model the app uses: 86% correct, 5 confidently wrong answers, and about 200 questions a minute on one A100.
  • Qwen3.8-27B: 96% correct with no confidently wrong answers, but about five times slower.
  • gpt-oss-120b: no more accurate than the 20b, at less than half the speed.

All three asked for clarification every time they should have, and the SQL check caught every write that gpt-oss-20b attempted.

With cryptic names

Every open model lost between 22 and 39 points. The new mistakes were the ones readable names used to prevent: a guessed column, or a table misread from its abbreviation. None of the open models let a write through.

  • gpt-oss-20b: fell from 86% to 46% correct, with 17 confidently wrong answers.
  • Qwen3.8-27B: the best open model, at 70% correct with 8 confidently wrong answers.
  • Gemini 3.8 Flash: the best overall, at 72% correct with just one confidently wrong answer, because it asked back rather than guessed.
  • Claude Sonnet 5, GPT-5.5, and GPT-4.1: 68 to 70% correct, but with 9 to 18 confidently wrong answers.
  • GPT-6 Luna: took caution too far, asking back on 53 of 69 questions and getting only 22% right.

The closed models are there for comparison only. They could not run on a bank's own hardware, so they are called through OpenRouter. Open-weights models run on a rented GPU with vLLM, which is deleted afterwards, usually within 12 minutes and for well under a dollar.

Same model, different servers

The app talks to any OpenAI-compatible endpoint, so moving from a hosted provider to a bank's own servers looks like a simple configuration change. A separate evaluation harness checks whether it really is. The same gpt-oss-20b weights were served by a hosted provider, on CPU, and on rented GPUs through llama.cpp, vLLM, and SGLang.

Every server chose the right tables. The differences appeared elsewhere: in which optional joins a draft added, in whether a destructive request was refused or caught later by the SQL check, and under load. vLLM kept the strict JSON format with 64 requests in flight and reached about 270 questions a minute on a single RTX 4090. SGLang broke that format under load until it was started with a stricter setting, a failure that never appeared one request at a time.

Another experiment rewrote the catalog with mainframe-style abbreviated names. With the table and column descriptions kept, both models still passed all twelve baseline questions. With the descriptions removed, only half passed, a clear sign that good metadata matters as much as the model.

Ten hard questions from the benchmark, from a wide desktop to a small phone. The human stays in the loop

The app drafts SQL; it never connects to a banking warehouse and never executes a query. Users edit or copy the result and run it separately in their own database client. The browser never receives the model API key.

Automated checks cover read-only statement shape and known table references. SQL syntax, column references, and business meaning still require human review. All warehouse names, relationships, and measures in the repository are synthetic test material rather than approved banking definitions.

Under the hood

The deployed proof of concept runs a Node backend and Elasticsearch as rootless containers on an Oracle Ampere A1 instance, and drafts SQL with gpt-oss-20b through a hosted provider. The repository also documents a broader future architecture, clearly separated from the smaller deployed POC.
